## 0. 一页结论

| 项 | 结论 |
|---|---|
| **推荐架构** | **Python CLI 为主干 + AGH ACP 为可选增强**（不是「全部转交 AGH」） |
| 为什么不走「全转 AGH」 | 实测发现模型会走 `tool_search` 去找 `sciret_*`，而该通道覆盖不到第三方 row（**非装载问题**，见 §2.4）→ 每次多一轮无效搜索 + 一句"工具不存在"的 confabulation |
| AGH 能不能接 | **能**。`agh --mode acp` 提供完整双向 JSON-RPC，已实测跑通握手→建会话→流式事件→终态 |
| 系统提示词注入 | AGH **没有 system prompt 字段**，只能作为首个 user 消息的前缀注入（详见 §5） |
| 现在的可用底座 | `python -m paper_agent.cli` 直调**完全可用**，一行 JSON 出参，零第三方依赖 |

## 1. 实测到的 AGH 接入面

### 1.1 ACP over stdio（唯一真正可编程的入口）

```bash
node <AGH>/packages/cli/dist/local/agnes.mjs --mode acp --profile <profile>
```

**实测握手结果**（原样摘录）：

```json
{"jsonrpc":"2.0","id":1,"result":{
  "protocolVersion":1,
  "agentCapabilities":{"loadSession":true,
    "promptCapabilities":{"image":true,"audio":false,"embeddedContext":false}},
  "_meta":{"agnes":{"agnesVersion":"0.0.0","apis":"call apis.list"}}}}
```

调用序列（**顺序有严格要求**）：

| 步 | 方法 | 方向 | 说明 |
|---|---|---|---|
| 1 | `initialize` | c2s | 必须先握手 |
| 2 | `_agnes/v1/workspace.add` | c2s | 注册工作区（`cwd` 需绝对路径） |
| 3 | `session/new` | c2s | 返回 `sessionId` |
| 4 | `session/prompt` | c2s | 发消息，**此调用会阻塞整个 turn** |
| 5 | `session/update` | s2c | 流式事件通知（**逐块到达**） |
| 6 | `session/request_permission` | s2c | 工具审批，**必须客户端应答否则卡死** |
| 7 | `session/prompt` 的 result | — | `{"stopReason":"end_turn"}` = 正常终态 |

### 1.2 实测拿到的帧形态（前端数据契约的依据）

**流式文本**——是逐块增量，不是整段：

```json
{"method":"session/update","params":{"update":{
  "sessionUpdate":"agent_message_chunk",
  "content":{"type":"text","text":"我是一个"}}}}
```

同一次回答实测收到 4 个 chunk 拼成完整句子 → **前端必须做增量拼接，不能覆盖**。

**工具调用**：

```json
{"method":"session/update","params":{"update":{
  "sessionUpdate":"tool_call","toolCallId":"t0-956de95a...","title":"tool_search",
  "kind":"other","status":"pending","rawInput":{"query":"sciret_plan"}}}}
```

`status` 取值实测有 `pending` / `completed`；配对的 `tool_call_update` 用同一 `toolCallId` 回填结果。

**事件全集**（读自 `packages/protocol/schema/acp/schema.json`）：
`user_message_chunk`、`agent_message_chunk`、`agent_thought_chunk`、`tool_call`、`tool_call_update`、`plan`、`available_commands_update`、`current_mode_update`、`config_option_update` 等。

**终态**：
```json
{"id":N,"result":{"stopReason":"end_turn",
  "_meta":{"ai.agnes.harness":{"phase":"terminalQuiescence","turnEnd":{"reason":"completed"}}}}}
```

> ⚠️ **实测坑**：同一轮会先来一串 **preview 流**（完整整段文本），随后才是真实的**逐块流**。
> 前端必须按 `promptTurnId` 或「后到者覆盖同名流」区分，否则会**重复渲染两遍答案**。

### 1.3 其他被排除的路径（省得你走弯路）

| 路径 | 结论 |
|---|---|
| `agh -p --mode json` | ❌ **无头环境挂起**，实测 280s 零输出。README 已注明需真实终端 |
| `agh serve`（Web 管理页） | ❌ 静态站 + 固定业务路由，非通用 API；且 Host 头白名单锁死 `127.0.0.1:<port>` |
| `agh serve model-api` | ❌ **源码中查无此实现**，仅存在于 usage 文本里（`args.ts:225`），是残留文案 |
| daemon socket 直连 | ⚠️ 需自实现 JSON-RPC 帧 + 凭证，收益不比 ACP 高 |
| `agh export <id>` | ✅ 可导出历史会话，但**只能事后导**，不能实时流 |

## 2.🔴 插件工具"搜不到"（原写"装载不上"，已更正，见 §2.4）

这是**本次调研最重要的发现**，直接决定架构选型。

### 2.1 现象

模型被要求调用 `sciret_plan` 时，**回答「工具不存在」**：

```
TOOL_CALL tool_search {"query":"sciret_plan"}
TOOL_UPDATE  status=completed  content=[{"text":"no matching tools or ready Skills"}]
```

模型自述可用工具只有：`read/write/edit/find/grep/ls`、`shell`、`computer_use`、
`web_fetch`、`subagent_*`、`tool_search/tool_describe`、`compact/todo` — **没有任何 sciret_\***。

### 2.2 已排除的原因

| 假设 | 验证方式 | 结果 |
|---|---|---|
| 环境变量没注入 | `printenv paper-agent_ROOT` | ✅ 变量存在且正确 |
| 没注册工作区 | 补 `_agnes/v1/workspace.add` 后重试 | ❌ 无变化 |
| daemon 快照过期 | `daemon stop` + `start` + 复检 | ❌ 无变化 |
| 插件代码写错 | 直接 `import()` 拷贝点 + 模拟 ctx | ✅ **成功注册全部 7 个工具** |
| surface 不含 acp | 查 `presets/standard.yaml` | ✅ `surfaces: [cli, sdk, acp, daemon]` **含 acp** |
| 没装/没信任 | `package status` | ✅ `actual=running trusted=true` |

### 2.3 决定性证据

```bash
$ agh doctor extensions --json
# 12 个 extension，全部是 agnes/tools-core、agnes/tools-web 等 builtin
# grep -i paper → 无输出
```

`agnes-lock.json` 里 `paper-agent-tools` 状态齐全（installed/trusted/enabled），
但 **`ext:paper-agent/tools` 从未出现在已加载 extension 列表中**。

插件代码本身没问题（能导出、能 `apply`、能注册 7 个工具），
**是 AGH 没有把它的 extension 装载进 worker**（← **❌ 此结论为误判，见 §2.4**）。

> 📌 **注意**：本节结论已被 §2.4 更正，以上内容保留作为排查过程的记录。
> 下面这段是同一结论的重复残留（初版文档的结构遗留），一并保留仅为对照，
> **其中"链路不通"的推论不成立**——链路口是通的，失效的是模型侧的检索习惯。

### 2.4 🔴 更正（2026-10-05 晚间，追查到底后）

**上面的结论是错的。插件装载一直正常，「工具不存在」另有原因。**

错在哪：把 `agh doctor extensions` 里 grep 不到 `paper-agent` 当成了阻断证据。
但那个命令的口径决定了它**根本不可能包含第三方 Cordis row**：

- `host.ready` 事件在 runtime tree apply **之前**触发（`packages/host/src/assemble.ts`），
  此时第三方 row 还是 `dormant` 状态，不进 status book → 计数恰好 12。
- 该命令另外还会 `assembleLocalHost` 另起一个 Host，而非查询运行中的 worker。

实测证据（本机，`~/.agh/data/audit/host.jsonl`）：

| 检查项 | 结果 |
|---|---|
| `extension.registered` for `ext:paper-agent/tools` | **7 条**，7 个 `sciret_*` 工具逐个在册 |
| `extension.failed` | 全库 **0** 条，不存在任何静默失败 |
| 生命周期 | daemon 停止 → `revoked reason=unload`；启动 → 重新 `loaded`。9 次 revoke 全是 daemon 生命周期事件 |
| 插件 meta | `deferLoading: false`，8 键齐全，符合 AGH 契约 |
| **AGH 自带回归测试** `plugin-extension.test.ts` | 11/11 通过，其中 `keeps the wire system string byte-identical while adding an eagerly disclosed tool` 断言第三方工具进了发给模型的 tools 数组 ✓ |

**真正的根因是模型走了 `tool_search`**，而 `tool_search` 的两个通道都覆盖不到第三方 row：

1. **完全相等通道**（`search-tools.ts`）：`ctx.tools.list()` 归一化后**全等**匹配——
   第三方工具确实在这里（`Kernel.tools`），但模型传的是模糊 query，不命中。
2. **模糊子串通道**：读 `tool_index`表。这张表全库**只有一条写入路径**
   —— `mcp-server` 扩展的 `onCatalog`，且要求 `cfg.defer=true`。
   第三方 row 不经过它，两者**没有任何同步代码**。本机没配 MCP server，这张表是空的。

所以准确表述是：**模型「看得见定义，但搜不到」**，而不是「看不见」。
模型自述"我没有任何 sciret_*"是它对自身工具清单的**记述不可靠（confabulation）**。

**修复选项**（按代价排序）：

| 方案 | 代价 | 说明 |
|---|---|---|
| **1. 提示里直呼全名** | 零代码 | 明确指示"直接调用 `sciret_plan`，不要搜索"。⚠️ **已被实测否掉，见 §2.5**（只对"工具在但搜不到"有效） |
| **2. 让 `tool_search` 模糊匹配回落到 `ctx.tools.list()`** | 1 文件 ~10 行 | 语义上最正确（这才该是 tool_search 的职责），需补测试 |
| 3. 把插件 row 写入 `tool_index` | 跨包改动 | 对 `deferLoading:false` 的工具语义多余，还要处理重名冲突与卸载竞态 |
| 4. ~~改 `deferLoading: true`~~ | 反向恶化 | 工具退到 deferred，模型**真正**看不见定义 |

> **M5 已结项**：这不是 AGH 的 bug，无需改 AGH 代码。
>
> ⚠️ 但 §2.4 的"无需改"只针对 daemon 模式。**ACP 模式另有一问，见 §2.5。**

## 2.5 🔴 最终更正：daemon 模式装载正常，ACP 模式根本不装载

§2.4 说"插件装载一直正常"——**只对了一半**。M4 立项期间实测 ACP 通道时发现了真相：

> **AGH 有三条启动路径，只有一条装载第三方插件。**

| 入口 | 代码位置 | 走哪 | 第三方插件 |
|---|---|---|---|
| **网页端**（`agh serve`） | `launch/web-command.ts:118` | `ensureLocalBackend` → 共享 daemon | ✅ 能调 |
| **普通 CLI 会话** | `boot/default.ts:28` | `ensureLocalBackend` → 共享 daemon | ✅ 能调 |
| **ACP 模式** | `boot/default.ts:25` | `bootLocal` → **自建一次性 Host** | ❌ **调不到** |

关键代码（`packages/cli/src/boot/default.ts:24-28`）：

```ts
if (p.connect !== undefined) return bootConnect(p, deps)
if (options.useEmbedded || p.standalone || p.ephemeral || p.mode === 'acp' || ...)
  return bootLocal(p, deps)          // ← ACP 在此被提前拦下，自建 Host
const backend = await ensureLocalBackend({...})  // ← 网页端 / 普通会话走这里
```

### 证据（本机实测，非推测）

| 检查 | 结果 |
|---|---|
| ACP 进程的 `host.ready` | 恒为 `extensions: 12`（全builtin），**从未出现 `extension.registered`** |
| daemon 侧同一份 lock | 有 `extension.registered`，`detail.row = "ext:paper-agent/tools"`，7 个工具逐个在册 |
| ACP 会话里调`read` 工具 | ✅ **成功读出探针文件内容** → 说明 ACP 的工具调用/执行机制本身完全正常，缺的只是第三方包 |
| 写 `profile.yaml` 声明插件 | ACP **直接启动失败**：`E_EXT_LOAD: trusted package has no immutable runtime snapshot`（与 `assemble.ts:448` 逐字一致）→ 已回滚 |
| `--connect` + acp 这条退路 | ❌ 走不通。`bootConnect` 不产 `endpoint`，`modes/acp.ts:15` 直接抛 UsageError |

双重不可达的原因：
1. `bootLocal` 的 `createHost`（`boot/local.ts:136-151`）**不传 `runtimePluginSnapshots`**；
2. `profile/resolve.ts:403` 只遍历 `m.packages`（profile 清单）而非 lock（已装清单），
   而 `buildOrdinaryRows`（`assemble/ordinary-rows.ts:45`）对不在 `profile.packages` 里的包**静默 `continue`**。

### 由此，方案 1（提示层规避）被实测否掉

探针里明确写了「禁止调用 tool_search，直呼 `sciret_plan` 全名」，模型**仍然先调了 3 次
`tool_search`**，拿回 `no matching tools or ready Skills`。

**原因**：工具压根没进ACP 那个 Host，写多少遍全名都没用。**提示层规避只对"工具在但搜不到"有效
（§2.4 的场景），对"工具没装载"完全无效。**

### 修复代价（若坚持让 ACP 用上插件）

必须**同时**改两处，单改任一处都会静默失效或硬失败：

1. `packages/host/src/profile/resolve.ts:403` — 遍历源扩展为「profile 清单 ∪ 已安装的
   trusted+enabled+treeIntegrity 包」；
2. `packages/cli/src/boot/local.ts:136-151` — `createHost` options 补 `runtimePluginSnapshots` /
   `runtimePluginSources`（照抄 `worker-runtime/src/main.ts:335-336, 379-391`）。

改完需重建 AGH。**属于改动第三方仓库，本项目不做。**

### ★ 但这不影响架构选型——因为插件本身不含科研能力

查`plugins/paper-agent-tools/index.mjs:153`，7 个工具**每一个都是同一层转接**：

```js
const proc = spawn(py, argv, { env, cwd: root, stdio: [...] });
//            ↑ python -m paper_agent.cli plan --goal "..."
```

文件头注释自述：「JS 仅做参数序列化 + 子进程调用 + 结果包装；**全部科研业务在 Python CLI**」。

所以 ACP 调不到插件，**丢的只是"转接器"，不是任何一项科研能力**。三条入口殊途同归：

| 入口 | 状态 |
|---|---|
| 网页端 + AGH → 插件 → spawn Python | ✅ 你实测能调 |
| 前端 → 后端 → spawn Python（M1） | ✅ 已用真实数据跑通 |
| 直接 `python -m paper_agent.cli` | ✅ 本轮再次验证 |

**因此 M4 已关闭**（2026-10-05 决策，见 §8）：ACP 通道最多只剩"对已完成的 run 做问答/综述"，
链路虽通但模型无法自己查数据，收益不足以投入。**关键点是：这不影响任何科研能力**——
流水线的实现与 AGH 无关。

## 3. 推荐架构

### 3.1 为什么不让 AGH 当唯一主干

原设想是「前端 → 后端 → AGH → 结果」。但：

1. ~~§2 的阻断项让工具链在 AGH 里跑不起来~~ —— **此理由已失效**（§2.4）。
   工具链在 daemon 侧是通的；即使 ACP 侧不通（§2.5），丢的也只是转接器而非科研能力。
2. **科研流水线本身不需要 LLM 来编排** —— P1–P5 / R1–R6 是确定性状态机，
   用 LLM 编排反而引入不确定性；
3. 项目的核心卖点是**可复现 + 证据可溯源**（哈希链、来源降级记录），
   这恰恰是「让模型自由发挥」最会破坏的东西；
4. **成本与延迟**：每步真实耗时 8–12 秒且要联网，走模型编排会再加一层不可控开销。
5. **插件层不含科研能力**（§2.5）—— 7 个工具只是 `spawn` Python 的壳，
   所以"让 AGH 当唯一主干"并不会获得任何额外科研能力，只是多一层可断的依赖。

> 所以架构结论不变（Python 主干 + AGH 可选增强），但**理由从"链路不通"换成了
> "确定性流水线不该由 LLM 编排"**。这个理由更站得住脚，且不受 §2.4/§2.5 更正影响。
>
> §2.5 的追查反而**验证**了这个选型：AGH 装不上插件这件事，恰好说明科研能力压根不该
> 依附于 AGH 生态——它全在 Python 里，谁调都一样。

### 3.2 推荐：双通道（Python 主干 + AGH 增强）

```
┌─────────────────────────────────────────────────────────┐
│  浏览器（已完成的 UI 设计稿三界面）                        │
└───────────────────────┬─────────────────────────────────┘
                        │ HTTP + SSE
┌───────────────────────▼─────────────────────────────────┐
│  后端服务（新增，零第三方依赖：只用 node:http / 标准库）    │
│                                                          │
│  ① 编排器 Orchestrator                                   │
│     持有 run_id 状态机，直接 spawn Python CLI（主干）      │
│                                                          │
│  ② 提示词注入器                                           │
│     把系统提示词作为首个 user 消息前缀                      │
│                                                          │
│  ③ ACP 客户端（可选增强，AGH 恢复后启用）                  │
└──────┬─────────────────────────────┬───────────────────┘
       │                             │
       │ spawn                       │ ACP over stdio
       ▼                             ▼
┌──────────────┐            ┌──────────────────┐
│ paper-agent  │            │  AGH（对话/解释）  │
│ Python CLI   │            │  模型不碰工具      │
│ （确定性）    │            │  只做解读/追问      │
└──────┬───────┘            └──────────────────┘
       │ 写产物
       ▼
runs/<run_id>/  ← 前端直接读这些文件渲染证据页
```

**分工**：

- **Python CLI 干实事**：plan / run-step / verify / report / cite，
  产出 `state.json`、`provenance.jsonl`、`conclusions.jsonl`、`report.md`。
  实测可用（见 §3.3）。
- **AGH 干解释**：用户问「这批文献的方法论演进是怎样的」这类**不跑流水线**的问题，
  走 ACP；即使工具不可用也能答得很好。
- **前端永不依赖 AGH 决定是否跑流水线** → §2 的阻断项**不再是阻断项**。

### 3.3 已实测可用的调用样例

```bash
$ PYTHONPATH=core python -m paper_agent.cli status --run run-20261005-074406-666d16
{"attempts":{...},"cmd":"status","degraded":true,"ok":true,
 "run_id":"run-20261005-074406-666d16","run_status":"RUNNING",
 "steps":{"R1_search":"DONE",...},"workflow":"research"}
```

**一行 JSON、无 TTY 依赖、无需 daemon** —— 正是后端编排器需要的形态。

全部 18 个子命令：
`plan / status / run-step / step-driven / finish / next / run-all / resume /
verify / report / cite / search-papers / parse-paper / analyze-paper /
verify-facts / write-review / self-review / eval / freeze`

## 4. API 契约（建议稿）

### 4.1 创建任务

```
POST /api/runs
{
  "goal": "大语言模型幻觉缓解方法",
  "workflow": "research",          // research | materials
  "lit_source": "auto"             // auto | arxiv | crossref | openalex | semantic_scholar
}
→ 201 { "run_id": "run-2026...", "state": {...} }
```

### 4.2 推进（前端主按钮）

```
POST /api/runs/{run_id}/step        { "step": "R1_search" }
POST /api/runs/{run_id}/run-all
→ 200 { "ok": true, "state": {...} }
```

### 4.3 事件流（对应 UI 的工具调用卡 + 步骤条）

```
GET /api/runs/{run_id}/events       （SSE）
event: step        {"step":"R1_search","status":"DONE","elapsed_ms":4200}
event: tool        {"tool":"sciret_run_step","step":"R1_search","sources":{"arxiv":"ok:10",...}}
event: degraded    {"source":"semantic_scholar","reason":"unavailable:HTTPError"}
event: conclusion  {"cid":"C1","text":"...","evidence_ids":["EV-0001",...]}
event: done        {"run_status":"COMPLETED"}
```

> `degraded` 是**特色而非错误**：四源里挂一个会自动切源并记录。
> UI 上应用橙色「已降级」而不是红色「失败」。

### 4.4 证据溯源（对应 UI 界面二）

```
GET /api/runs/{run_id}/evidence
→ { "provenance": [...], "factcheck": {...}, "review": {...} }
```

数据来源已确认的三个文件：

| 文件 | 内容 |
|---|---|
| `provenance.jsonl` | `ev_id / kind(fact·artifact) / ref(DOI) / sha256 / chain_hash / tier` |
| `conclusions.jsonl` | `cid / text / evidence_ids[]` — 结论↔证据绑定 |
| `factcheck/factcheck.json` | `citations.consistency_rate / results[].claim` |

## 5. 系统提示词注入

### 5.1 AGH 没有 system prompt 字段

读 `protocol/schema/acp/schema.json` 确认：`session/new` 只有 `cwd` /
`additionalDirectories` / `mcpServers` / `_meta`；`session/prompt` 只有
`sessionId` / `prompt[]` / `_meta`。AGH 的系统提示词是**内置 section**
（`persona` / `environment` / `coding-doctrine` 等，见 `packages/code/src/prompts/sections.ts`），
**不开放运行时注入**。

### 5.2 建议做法：首轮前缀 + 明示

**第一轮**注入，之后不再重复（省 token、避免干扰）：

```
【角色】你是一个科研文献分析助手。
【硬约束】
1. 只使用已提供的检索结果作答，不得凭记忆补充文献；
2. 每条结论必须标注来源编号；
3. 资料不足时明确说「证据不足」，不要编造。
【工作流】research：R1_search → R2_read → R3_analyze → R4_verify → R5_write → R6_review
【本次目标】{goal}
```

**前端必须把这段提示词显示给用户**（UI 设计稿已按此设计）—— 用户有权知道
「我输入的话被加了什么」，这对科研工具的可信度是加分项而不是减分项。

> ⚠️ 走 Python 主干时，`goal` 是参数直接传给 CLI 的，比塞进提示词**更干净**；
> 提示词主要服务于 AGH 那个「解读/追问」的增强通道。

## 6. 建议的 HTTP 层设计

```
浏览器 ──HTTP POST──▶ 后端 ──spawn──▶ paper_agent.cli
   │                                    │
   │◀──────SSE 事件流───────────────────┘
   │
   └─(可选) ACP over stdio ──▶ AGH
```

关键取舍：

- **端口**：建议 `8787`，避开 AGH 的 `4177`。
- **绑定**：`127.0.0.1` only。多人部署需另加认证，**本轮不做**。
- **SSE 而非 WebSocket**：事件是单向的，SSE 足够且实现更简单。
- **零第三方依赖**：沿用项目的红线，用 `node:http` 手写，部署无需 `npm install`。

**关闭理由：收益不足，不是技术阻塞。**

**不做任何AGH 源码改动。** 修复 ACP 装载需同时改 `profile/resolve.ts:403` 与
`boot/local.ts:136-151` 并重建 AGH，属第三方仓库，且单改任一处会静默失效或硬失败——
投入产出比不合适。

**将来若重启 M4**，路径是已知的：
1. 后端加 `server/acp.js`（ACP over stdio 客户端，零依赖）；
2. `POST /api/runs/{id}/ask` 把 `runs/<id>/` 产物作为上下文喂给模型，
   前端按 `promptTurnId` 去重preview 流与真实流（§1.2）；
3. `session/request_permission` 必须带 60s 超时兜底防卡死。
